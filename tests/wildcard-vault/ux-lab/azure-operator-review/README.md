# Azure operator harness: isolated preparation

This partial copy is based on the old `33be67d6` UX prototype. It is not a release candidate, has no live Azure startup, and does not modify product or qualification workflows. `run.ps1` deliberately rejects Azure `Up` until the identity and package-acceptance path is implemented and reviewed.

The runner uses the adjacent UX fixture. The isolated Azure role composition is not yet connected to `Up`; the local journey bridge requires already-created, explicitly identified role containers.

For Azure and OpenBao package acceptance, authenticate the immutable producer artifact first. Set `-SuppliedPackageDirectory` to the downloaded receipt, archive and SHA-256 sidecar directory, and supply `-SuppliedProducerRunId`, `-SuppliedArtifactId` and `-SuppliedArchiveSha256`. The runner checks the final package contract and copies the three original files into the lab. The staged identity tracks that copy. The producer workflow authenticates its origin.

The narrow OpenBao operator scenario is `-CertificateMode ordinary -MaterialProvider openbao-kv2 -PackageAcceptance`; `Test` requires `-Phase all`. It covers the public operator journey with packaged Node processes in containers, not a native/systemd installation: existing `systemdQualified=false` and `publishedReleaseQualified=false` remain unchanged. `-NativeOpenBao` adds a temporary installed-only consumer on an owned, trusted Linux runner. Both host transports are pinned HTTPS over loopback. The AppRole reads only the selected version, and the journey verifies the installed leaf and chain against the fixture's real ACME CA. Run the explicit owned cleanup even after interruption. The native option still requires the trusted workflow integration and real-host review.


`Stop` intentionally retains volumes and is not teardown evidence. `Cleanup` invokes `owned-teardown.cjs` through the Docker CLI adapter after requiring an explicit project-matching receipt. It checks labels, removes only owned project containers, volumes and networks, and verifies their absence; it never invokes global prune. Tests use a fake Docker transport, and the receipt is caller-declared rather than authenticated. Review, exclusive project ownership and independent cleanup verification are required; Docker label checks and deletion are separate operations and do not prevent a concurrent ownership change between them.

`compose.azure.isolated.yaml` is a standalone role-service draft, not wired into `Up`: issuer and consumer have separate UIDs, writable state and read-only sink mounts. `sink-isolation.cjs` checks Linux ownership, restrictive mode bits and non-overlapping sink roots without reading credentials. It does not verify POSIX ACLs, mount namespace behavior, broker isolation, configuration paths, or real cross-role denial. The host-side token-file renewal and actual isolated service/journey integration must be implemented and tested before removing the Azure startup guard.

`isolated-journey-run.cjs` starts the public journey with an authenticated loopback bridge. Docker transport pins the exact role container IDs and rechecks project and service labels for each request. Package proof requires matching independently checked role copies. This does not start containers or complete the Azure journey; an extra issuer remains unsupported.

The host broker must acquire each role's token separately and hold all OIDC assertions outside both containers. Each role gets only its own read-only directory bind; do not bind the individual token file, since atomic rename would leave a file bind stale. `token-sink-writer.cjs` accepts an `acquire()` callback returning `{accessToken, expiresOn}` (expiry in epoch milliseconds) and a `prepareOwner(fd)` callback; it writes a fresh file in that directory and atomically renames it to `token.json`. The broker must schedule refresh before expiry, enforce UID/mode/ACL ownership, protect directory replacement, observe failures, and stop without exposing credentials. These primitives do not themselves establish identity or cross-role denial.

`cross-role-probes.cjs` prepares own-role and reciprocal wrong-client workload exchanges using injected protected assertion reads and the existing `requestJson`; exact reviewed federation-mismatch codes are required. `token-file-rbac-probe.cjs` prepares an exact-version read and 403-only consumer write denial using the existing credential getter and transport. Its disposable probe secret must already be explicitly owned and scoped; the intent is recorded before the PUT because a wrongly authorized write can create a version. The external cleanup owner must remove and verify the owned probe. Network failure, 401 and unexpected success never count as authorization denial. These are unexecuted supporting probes, not qualification.

`final-evidence-bridge.cjs` statically imports the validator from the trusted workflow checkout. Commit `5ac8b05578a0d48c917dc1cc4ffeb1c0eed5e19a` identifies the reviewed contract; it is not a dynamic loading mechanism. The bridge emits the strict profile only after the observed journey and same-run cleanup both validate. The OpenBao journey can measure a consumer routed to an owned systemd host with an authenticated package and restart controller. The Docker bootstrap does not supply that controller. IMDS and natural-expiry remain separate profiles; no producer is supplied here.

Package acceptance requires explicit immutable API and worker image IDs. `candidate-images.cjs` checks their actual image IDs and source-SHA labels and records them; labels alone do not authenticate producer provenance. The shared `tt-core-api:36ff` backend is not the candidate and lacks required lifecycle actions. Azure `Up` remains blocked.

Supported agent inputs are token-file, workload-identity and managed-identity. The local adapter rejects shared token paths, duplicate principal labels, shared workload assertion paths, identical declared issuer/subject/audience trusts, duplicate workload client IDs, and managed identities declared on the same host. `rejectSharedAssertionBytes` can additionally reject identical assertion contents without printing them. These are fail-closed prechecks only; claims or file paths cannot prove actual principal or Azure permissions. They are not yet wired into live startup.

Before a run, independently establish separate renewable identities, protected mounts, reviewed federation trusts, cross-role exchange denial, scoped consumer reads and write denial. Shared OIDC trust is insufficient. The draft role services use different UIDs and state volumes, but their boundary has not been validated live. Never record assertions, tokens or private material in receipts.

For the retained-version drift action, the Azure branch now calls the installed package's existing material-store client with the exact opaque Azure provider version; Vault direct reads remain in the Vault branch. Azure revocation/rotation still fails closed: the prototype's Vault Agent role/sink controls do not implement Azure renewal or revocation, and no real isolation or fault mechanism is assumed. A live journey also needs installed-service rather than container-process qualification, an explicit real committed-write/lost-response mechanism without weakening TLS, independent served-TLS verification and owned cleanup. Do not remove the fail-closed Azure startup guard before those parts and independent review are complete.
