# Disposable domain-backed AD CS lab

This infrastructure is for the scenarios that require a real AD forest and enterprise CA. It supplements hosted Windows qualification. It does not provision a permanent lab or a self-hosted runner.

Directory administration and enrollment ACLs identify domain administrators, forest administrators and domain computers by the actual domain SID and their [fixed group RIDs](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/understand-security-identifiers). They do not depend on English group display names; officer group membership and the domain computer group are checked before CA/template configuration. This is required when the DE/FR display language is installed before forest creation.

The separate `certops-enterprise-adcs-hierarchy-qualification.yml` profile adds one temporary Windows Server 2022 VM for a genuine standalone root and enterprise subordinate hierarchy. The root signs the subordinate's native CA CSR, publishes its public CA certificate and CRL through private HTTP, then stops and disables its signing service. The domain CA accepts the signed response against its native key. The installed LocalSystem agent issues and deploys RSA 2048/3072/4096 and ECDSA P-256/P-384 leaves through the subordinate; independent native online chain observations must contain exactly the leaf, subordinate and offline root. The suite separately observes the root signing service stopped and its public CRL available. It requires every named hierarchy scenario in the committed qualification metadata: the baseline cases except the root-CA renewal/key-rotation cases, plus the hierarchy-specific checks. Subordinate CA renewal needs a new parent signing ceremony and is not claimed by this profile. Only this profile pays for a fourth VM; the usual root-CA lab remains three VMs. No Azure hierarchy execution has been performed during implementation.

The mandatory native reconciliation slice runs the production issuer and bounded
SPKI candidate search under the independently measured LocalSystem identity.
A read-only CA database checkpoint proves an empty search window beyond the
actual CA head, and the original signed leaf must be the unique matching
candidate. One deliberately submitted copy of the owned public CSR then creates
exactly one additional actual CA request and another signed leaf with the same
SPKI; the search must report two matches and refuse automatic attachment. An
explicit actual candidate can pass the SPKI-selection boundary, while the public
API must refuse reconciliation of an already installed enrollment. Journal,
watermark and trusted current TLS remain unchanged, and only the duplicate CA
request is revoked during cleanup. This is native adapter integration. It does
not fabricate an uncertain enrollment or claim completed recovery through the
signed job lifecycle; that boundary remains in the observed fault experiments.
The added request occurs after the positive renewal count assertions and uses
an original RSA-4096 subject with no later fixed-count oracle.
The hierarchy profile imports its root into `LocalMachine\\Root` and its issuing CA into `LocalMachine\\CA`; trusting the subordinate as a root would hide a broken three-certificate chain and is expressly refused by the chain assertion. Standalone-root administration permits local administrative WinRM only within this owned private lab, and the member's TrustedHosts contains only the root's private address. Resource-group deletion removes those temporary settings and all CA private keys.

Native CA installation and publication follow Microsoft's [Certification Authority deployment guidance](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2012-r2-and-2012/hh831574(v=ws.11)) and the documented [`certutil -installCert` operation](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/certutil#-installcert). Source validation confirms syntax and infrastructure compilation; those checks do not confirm successful Windows role installation or issuance.

Independent TLS observations and persisted evidence verify issued certificates. Infrastructure receipts and scenario execution reports are separate artifacts; infrastructure readiness alone does not qualify these scenarios.

The member image is selectable as Windows Server 2019, 2022 or 2025, with native English, German or French qualification. German and French install actual matching Windows Server language CABs on both the CA and member, reboot, and verify display resource installation, LocalSystem UI language and system locale before native cases run. A missing or mismatched language package fails qualification. Manual dispatch accepts trusted `main` only, so the candidate and workflow must first be merged there. AD CS enrollment remains gated in normal release artifacts: this lab creates an isolated qualification build with the enrollment capability enabled and records that provenance. It does not publish that build or promote the release capability.

Pending continuation advances the supported scheduler eligibility clock to avoid fifteen-minute polling and fourteen-day expiry waits. CA decisions, signed dispatch, native key custody and TLS observations use actual host operations and clocks. CMC response decoding is exercised by native issuance; a distinct signed CMC renewal protocol is not claimed. Submission uncertainty and retention/adoption still need additional qualified host journeys; the twenty-three cases do not establish those outcomes. No Azure qualification execution has been performed while preparing this source.

## Prerequisites

Use a dedicated disposable Azure subscription and the GitHub environment `certops-adcs-lab`. Configure `AZURE_CLIENT_ID`, `AZURE_TENANT_ID` and `AZURE_SUBSCRIPTION_ID` as environment variables. The service principal must federate only the trusted repository's environment subject through GitHub OIDC. Give it rights to create and remove qualification resource groups and their VM/network resources inside this isolated subscription. It must not have rights over production resources. No Azure client secret is used.

Restrict both GitHub environments' deployment branches to `main`, including the janitor and experimental workflows. An environment-scoped OIDC subject alone does not encode a branch restriction; the environment rule and workflow condition must both hold.

For German/French, configure environment secret `CERTOPS_WINDOWS_LANGUAGE_ASSETS` as a JSON object keyed by `2022/de-DE`, `2019/de-DE`, `2025/de-DE` and corresponding `fr-FR` keys. Each selected key contains `uri` and `sha256` for the matching official Windows Server language CAB, copied from licensed Microsoft media to an owned HTTPS Azure Blob. The CA always needs the 2022 key; the member needs its selected version. Private blob access URLs are masked and excluded from reports. These licensed packages are not redistributed by this repository. Windows rejects incompatible CABs and the test additionally verifies actual installed resources. Follow Microsoft's [language packaging guidance](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/languages-overview) for matching media and servicing requirements.

The workflow accepts a bounded two-, four- or eight-hour expiry. Every group is named from the GitHub run/attempt, tagged with its purpose, candidate SHA, creation time and UTC expiry. Its generated VM/domain password exists only in masked runtime values and a temporary secure-parameter file. Guest Run Command transmits it through the Azure management plane; Azure administrators with access to the disposable group can inspect guest command state. Delete the group after the run. No raw command output or credential parameter files become workflow artifacts.

## Network and ownership

The DC/CA, Windows member and Linux host use private addresses in a unique virtual network. No VM has a public IP. An egress-only NAT gateway supports installation and Azure guest-agent connectivity without opening inbound listeners. The NSG rejects Internet ingress. The domain and privileged bootstrap account exist only in this isolated forest; they are not enterprise identities or production CA configurations.

Forest promotion and domain join use explicit reboots. Stage receipts record only allowlisted completion markers. The bootstrap scripts reject pre-existing domain/CA configurations. The installation has not been qualified until the real Azure workflow passes.

## Experimental submission response loss

`certops-enterprise-adcs-response-loss-experiment.yml` is a separate trusted manual experiment. It runs the native baseline and then observes an exact owned request in the real CA database before terminating only a still-running `certreq -submit` descendant of the owned agent service. Directory, service ancestry, process creation time and command identity checks fence the fault. A missed timing window fails explicitly. It never rewrites database state, substitutes command output, or edits the agent's enrollment journal.

After a real uncertain submission, the experiment approves the exact CA request, proposes another fixture's RequestId and requires refusal without installation, then proposes the correct request and requires real TLS recovery. Its report is explicitly `not-qualified` and is excluded from the release matrix until actual lab runs establish the fault controller's reliability. This source has not been executed against Azure.

## Cleanup

The stopped-site case proves native binding rollback and retained accepted key custody. The supported session-only `POST /api/v1/workspaces/:id/certops/enrollments/:enrollmentId/retry-installation` action queues an audited signed continuation for an eligible failed installation; the native retry must reuse the accepted certificate and exact protected key without another CA request. The separate recovery action requires explicit acknowledgement of unknown effects for an orphaned operation. Focused API tests cover admission, requester provenance, concurrency and refusal; native recovery remains part of the host matrix.

The main workflow requests resource-group deletion in an unconditional cleanup step, including failed stages. `certops-adcs-lab-janitor.yml` independently runs hourly and removes expired groups only when both their name and ownership tag match. Configure a separate `certops-adcs-cleanup` GitHub environment for the janitor, restricted to trusted `main` and allowed to run without required reviewers or wait timers. Give it its own OIDC federated identity and environment-scoped `AZURE_CLIENT_ID`, `AZURE_TENANT_ID` and `AZURE_SUBSCRIPTION_ID` variables for the same dedicated lab subscription. Its Azure role needs resource-group read/delete and deletion of owned group contents; it needs no VM provisioning or language-asset credentials. Keep lab provisioning approvals on `certops-adcs-lab`: an approval waiting on that environment must not hold the expiry scan. Monitor its failures: cancellation or runner loss can prevent the main cleanup step, so the independent expiry scan is required before using this lab.

To inspect expiry decisions without deleting resources, authenticate the dedicated subscription and run `./infra/certops-adcs/remove-expired-labs.ps1 -WhatIf`. Never launch these scripts against an existing enterprise forest.

Local Bicep compilation and PowerShell parsing validate source syntax. They do not prove Azure quota, image availability, regional SKU support, AD DS startup, enterprise CA privileges or network behavior. Those require an actual disposable lab run. No infrastructure is launched by editing or compiling these files.

The committed `safety-cases.json` inventory covers every prohibited EKU both alone and mixed with Server Authentication, absent EKU, schema one, and wrong/mixed application policies. Actual key snapshots test RSA below template minimum, EC on schema two, and algorithm/curve mismatches on schema three and four. CA faults set the SAN-attribute bit, clear encrypted-request enforcement, and combine both; the real officer fixture records the original native DWORDs before any mutation, restores and rereads them afterward, and independently queries the CA database to prove refusal happened before submit. Each unsafe CA combination runs both with and without explicit local operator attestation, reloading the actual installed service configuration; known unsafe flags must remain unsafe and cannot be waived. Native CNG enumeration and certificate-store inspection must also show no generated key or installed leaf. These templates and policy faults exist only inside the disposable qualification forest. The inventory guard runs before Azure provisioning and fails if a mandatory safety family is omitted or mislabeled; two focused negative guard tests passed. All these additional native source cases remain unexecuted until the domain-backed qualification workflow runs.

Full native safety/lifecycle qualification uses a bounded four-hour lab TTL by default (eight hours is an explicit manual choice), a sixty-minute guest test deadline, and 150-minute baseline / 165-minute hierarchy workflow bounds to leave room for image, language, forest and tool setup plus verified teardown. Resources are still deleted immediately after the run; TTL and the independent janitor protect interruption rather than reserving a running lab. No timed native/Azure execution has yet established actual duration.

The per-profile manual renewal cases submit a new native CA enrollment for the existing managed certificate identity. They do not claim a CMC signed-renewal protocol. The separate positive renewal report entries record this distinction, measured template schema, actual old/new RequestIds and native key custody. All new domain-native cases remain unexecuted during implementation.

Immediately issued CMC responses expose the issued public certificate but may omit RequestID. The positive profile cases therefore obtain the real native CA RequestID through read-only CertificateAuthority.View queries constrained to the unique owned CommonName/requester and exact independently observed public leaf SHA-256 fingerprint. They do not populate or rewrite control-plane RequestIDs. Public DER retrieval uses the documented [IEnumCERTVIEWCOLUMN GetValue base64 output](https://learn.microsoft.com/en-us/windows/win32/api/certview/nf-certview-ienumcertviewcolumn-getvalue).

## Observed journal phase experiment

The separate trusted manual `certops-enterprise-adcs-journal-phase-experiment.yml` selects `keygen_intent`, `prepared`, `submitting`, `installing`, `accepted-before-bind`, or `bound-before-complete`. It requires the actual durable native phase before interrupting only the independently identified owned service process tree. A missed fault window fails the experiment. It never writes the enrollment journal or rewrites database/host clocks. The isolated API and guest use the supported 60-second lease and 60-second hard grace, with coupled nonce timing; normal qualification lanes retain their defaults.

The [accepted-before-bind experiment](../../docs/certops/qualification/adcs/accepted-install-recovery-experiment.md) separately requires real accepted leaf/CNG private-key possession, unchanged outgoing IIS/HTTP.sys and trusted TLS, and a drained exact native tree before public acknowledged recovery. It must install the same leaf, CSR, container and RequestId without another CA request. Its wait budget derives from the actual persisted lease plus real worker grace. Unexpected descendants or missed windows preserve state and fail. Its strict twenty-source experimental report cannot substitute for a mandatory release report; this new phase has no native execution evidence yet.

The [bound-before-complete experiment](../../docs/certops/qualification/adcs/bound-install-recovery-experiment.md) instead requires the new native binding and trusted TLS while the durable journal still says `installing / bind`. This is not a pre-verification marker: verification and retention bookkeeping may already have occurred. It records the actual retention-row presence at interruption, then requires same-leaf/key/RequestId public recovery, fresh claim-bound verification evidence and one exact idempotent predecessor row with protected predecessor custody retained. Its separate current-source proof remains experimental and unexecuted; no additional release environment is qualified by its implementation.

For `keygen_intent`, the observer additionally requires an actual owned `certreq -new` process and protected CNG key; recovery must refuse the absent durable CSR, then public cancellation and signed terminal cleanup must remove the key with zero CA requests. Other phases require successful supported recovery. Recovery waits actual eligibility and the production lease reaper, preserves the original job's unknown-effects flag, then requires explicit public acknowledgement before a signed continuation. The experimental report is independently verified and remains `not-qualified`; baseline reports produced in an experimental context are also marked `experimental` and `not-qualified`. The release collector and matrix exclude these lanes. Hierarchy, response-loss and journal-phase experiments cannot share a lab. Every lane retains bounded resource lifetime, immediate verified teardown and the independent janitor. No journal-phase Azure or native Windows execution has been performed during implementation.

GitHub OIDC authentication refreshes at guest execution, report retrieval and teardown boundaries so long provisioning cannot leave cleanup relying on the initial login. Only the same dedicated lab identity/subscription is used, and cleanup still writes its outcome if authentication fails.

## Actual elapsed validation expiry

The mandatory native matrix includes `adcs-real-elapsed-validation-deadline-frees-unaccepted-key`. It uses the supported host-local `adcs.validationTimeoutSeconds=300` setting, public enrollment `pollInterval=60`, and a real program-scoped outbound LDAP fault for the actual chain-helper executable. The CA remains online and reachable by template preflight. A fresh helper must independently report `revocation_unknown`; a cache hit or ineffective firewall fault fails qualification.

After a genuine CA issuance enters `validation_deferred`, the test restores the original configuration and restarts the installed SYSTEM agent. Its persisted five-minute deadline must remain unchanged. The fixture waits at least five real monotonic minutes and calls the scheduler with its actual current time. It then requires the signed continuation and durable journal to report `validation_expired`, exact unaccepted CNG-key absence, no certificate acceptance or CA resubmission, and unchanged independently trusted outgoing IIS TLS. No native clock, journal deadline or database timestamp is rewritten. Firewall, configuration, chain-cache state and the unused issued certificate are cleaned up through their ownership guards.

The report explicitly identifies a configured five-minute window. It does not claim an observed 24-hour wait. The shipped default remains 24 hours and is checked separately by focused configuration/deadline tests. These native source cases remain unexecuted until the domain-backed workflow runs.

## Cancellation after genuine CA issuance, before local acceptance

The native baseline and hierarchy suites include
`adcs-real-cancel-ca-issued-unaccepted-key`. A real public pending enrollment
owns a nonexportable CNG key. The officer approves its actual CA row before the
ordinary fifteen-minute poll is due; independent public-leaf signature and CSR
SPKI checks prove issuance already happened while the server/journal still say
pending. Public cancellation and the default real-clock scheduler must dispatch
signed cleanup that deletes only that unaccepted key. The certificate must
never enter My/WebHosting, the existing trusted IIS endpoint must stay unchanged,
and no second CA request or terminal reconciliation revival is allowed. The
unused issued certificate is revoked in `finally`, including failure paths.
This is deterministic ordering of real actions, not an injected journal/clock
race; native execution remains pending. Its bounded `nativeIssuedCancellation`
report and current helper source are mandatory for both suites.
