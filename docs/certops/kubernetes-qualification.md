# Disposable Kubernetes qualification

The trusted manual `certops-kubernetes-qualification.yml` workflow uses Ubuntu 24.04, an isolated kind cluster, digest-pinned Kubernetes and a fixed cert-manager chart. It builds the candidate production controller image and loads that image into the owned cluster. The workflow never connects to an existing customer cluster.

The host suite exercises the Certificate provisioner with real Kubernetes resources, including Ready issuance, ownership and namespace boundaries, idempotency, and independent public certificate parsing. Production-image fixture pods exercise the shipped in-cluster client with mounted service-account credentials, list/watch and merge patch. A read-only pod must receive actual Kubernetes 403 responses for create and patch, with independent checks that the existing resource is unchanged and the refused resource absent.

The separate API E2E suite starts migrated PostgreSQL and the real API. A real administrator session creates an idempotent public provision intent. The unmodified production controller pod consumes its cluster-bound command using a scoped machine token, obtains authorization from the API, mutates its owned Certificate and reports actual list/watch observations. cert-manager issues the certificate. The persisted fingerprint must match independently parsed public `tls.crt`, and the workspace must contain no agent registration.

A destination pod consumes its own locally mounted TLS Secret. Only that destination reads its private key. The harness reads public certificate bytes and performs an actual TLS handshake through a loopback port forward; the peer fingerprint must match. The controller's optional Secret fallback uses the production bounded reader. Its role permits `get` only for the named destination Secret, with no Secret mutation, CertificateRequest mutation or deletion rights.

The public pause setting must refuse a new intent without creating a Kubernetes resource. For an API outage, the harness suspends only its own private TLS transport process, submits a real changed intent to the still-running API, and verifies that the destination remains unchanged. Resuming transport must allow the production controller to update the Certificate, cause genuine CA reissuance, persist the new public observation and retain earlier slot history. The destination reads updated Secret projections on SNI connections; its served leaf must eventually change too. A production deployment restart must preserve Certificate UID and completed-job count.

The private fixture TLS bridge forwards unchanged controller protocol requests to the loopback API. It runs as a separate child process so bounded kubectl waits cannot block delivery. Its self-signed public trust anchor is mounted into the controller via `NODE_EXTRA_CA_CERTS`; no TLS verification bypass is used for API delivery. It accepts only CertOps executor/job paths and logs no bodies or credentials. Destination certificate trust and fingerprint observations are fixture-scoped.

Cleanup stops the owned port forward and bridge, deletes only each suite's random namespace, removes temporary bridge key material and run-owned API accounts/workspaces, and then destroys the complete kind cluster and Compose volumes unconditionally. Artifacts contain sanitized named reports and public status only. Machine tokens, TLS keys, database files and pod logs are excluded.

Both Kubernetes suites have source implementation and syntax/lint checks. Actual kind execution remains pending. External issuers, HTTP-01 ingress, full renewal timing and remaining failure/permission permutations require separate scenarios; these initial suites do not complete every controller catalog specification.

The controller test suite also exercises the real Kubernetes client and observer against a bounded loopback HTTP protocol fixture. A streamed Kubernetes `Status` with `status: Failure` and numeric `code: 410` must trigger one fresh list, resume watching from that list's resource version, and deliver subsequent updates. The fixture uses no cluster, CA or simulated certificate issuance; it proves transport and recovery behavior, not actual etcd compaction. Native compaction qualification remains separate.
