# Native Linux consuming-server certificate reload qualification

The trusted-main manual `certops-nginx-qualification.yml` workflow runs six jobs: nginx, Apache, and HAProxy on disposable Ubuntu 22.04 and 24.04 hosts. The common `scripts/certops-nginx-host.js` harness retains its original filename and selects the actual service with `CERTOPS_RELOAD_SERVICE`. Each job installs its distribution package and records native server/OpenSSL versions. It starts a fresh owned process, private configuration, random loopback port, and temporary certificate destinations. The harness does not edit the host's ordinary service configuration or reload its default service.

Five mandatory cases per service cover initial trusted TLS, real certificate/key rotation followed by production validate-and-reload, invalid configuration refusal, a genuinely missing reload executable, and cleanup. The fixture generates fresh CA-signed certificates and verifies each served hostname and chain with the fresh public root. File replacement must leave the consuming server serving its original loaded leaf until the real reload command executes. After reload, bounded independent TLS polling must observe exactly the newly deployed fingerprint. Reports use separate service suite names and mandatory case prefixes; one server's success cannot replace another's qualification.

The harness uses the production filesystem deployment, local command policy, and reload modules. nginx profiles execute `nginx -t` and `nginx -s reload`. Apache profiles execute `apache2 -t` and `apache2 -k graceful` against the fixture's own PID file and explicit configuration; the actual non-root runner identity owns its workers. HAProxy validates with `haproxy -c`, starts in master/worker mode, and reloads its exact verified master PID with `SIGUSR2`. Its native `ssl-load-extra-files key` behavior consumes the separate local key destination without bundling private bytes into the public certificate file. These follow the [Apache process controls](https://httpd.apache.org/docs/2.4/programs/httpd.html) and [HAProxy master/worker and key-loading contract](https://www.haproxy.com/documentation/haproxy-configuration-manual/new/2-6r1/). Invalid configuration must fail at validation and leave the existing TLS leaf live. A missing reload executable must fail at the reload stage and preserve the live service. Neither failure is reported as a successful certificate cutover.

This is native executor and consuming-server coverage. It does not qualify public API dispatch, systemd supervision, a transaction spanning multiple targets, failed rollback, or a released agent package. The native workflow has not been executed during implementation; full CI execution remains pending.

Cleanup independently enumerates the original process group's native `/proc` members, refuses to signal unexpected executables, and stops the owned master/worker group with bounded graceful shutdown and forced termination when required. It requires the whole group to disappear even if the master already exited, verifies the loopback port can be bound again, and removes only its checked temporary-directory prefix. The disposable runner remains the independent interruption safeguard. Only sanitized named reports are uploaded; private keys, native server logs, configuration, and backup contents remain local.
