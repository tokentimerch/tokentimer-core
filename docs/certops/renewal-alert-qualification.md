# Renewal outbox and SMTP qualification

The separate manual `certops-renewal-alert-qualification.yml` workflow executes eight mandatory supporting integration scenarios against only an isolated API, PostgreSQL and MailHog. The source admits a renewal through the production job service, claims it using a genuinely registered protocol client, reports a fixture failure through the real authenticated result endpoint, drains the production outbox resolver and starts the actual delivery-worker process. An independent MailHog receipt must match the run-owned recipient and MIME-decoded renewal subject. Terminal replay, public first-issuance failure, requester approval rejection and a completed dry run must leave one owned renewal alert.

The delivery child uses `NODE_ENV=production` and actual SMTP transport against the loopback fixture. `NODE_ENV=test` in the email helper intentionally simulates success, so a successful delivery database row is insufficient. The workflow starts no background test-mode delivery worker, preventing that simulated branch from racing the mandatory real receipt.

All eight cases passed focused execution. Independent strict report verification, current source digest verification and lint passed; hosted/full CI remains pending. Agent-local admission metadata for a real locally generated certificate/key is explicitly seeded as an initial supporting protocol prerequisite. The fixture does not claim native custody, actual certificate renewal failure, real CA traffic or delivery to an external recipient. Shared development databases are refused by the separate-stack opt-in and empty global agent/certificate/alert/outbox guards. The owned API process and label-verified PostgreSQL/MailHog containers were removed after testing.
