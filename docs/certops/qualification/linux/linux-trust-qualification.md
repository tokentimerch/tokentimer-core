# Native Linux trust-store qualification

The manual `certops-linux-trust-qualification.yml` workflow runs only on trusted `main`. It uses disposable Ubuntu 22.04 and 24.04 GitHub-hosted machines and a digest-pinned AlmaLinux 9.6 container for the RHEL-family store. The report measures `/etc/os-release` and identifies whether the native store belongs to a VM or a container. Container coverage does not qualify systemd, SELinux enforcement, a RHEL subscription, or a complete RHEL host installation.

`scripts/certops-linux-trust.js` calls the production trust executor with real filesystem operations and real `update-ca-certificates` or `update-ca-trust extract` commands. The Debian revoke path explicitly supplies the supported `update-ca-certificates --fresh` command reference. No OS, executable, receipt, certificate, or platform responses are replaced with fixtures. Certificate keys and receipts exist only in a private temporary directory and are removed before completion. Uploaded artifacts contain named, sanitized reports only.

Eleven mandatory scenarios cover root installation, intermediate installation, fresh-process receipt replay, protection of an identical pre-existing anchor, invalid fingerprint/non-CA refusal, failed refresh recovery, corrupt receipt refusal, owned revocation, renewal-only local policy refusal, OS-success/receipt-finalization fault recovery, and cleanup. Fresh OpenSSL-generated chains are independently verified through the default derived OS trust store, without an explicit CA file. Verification must fail before installation and after removal; an unrelated pre-existing anchor must remain trusted. Receipt permissions and ownership are checked after replay.

The refresh fault uses a genuinely missing local executable as the resolved command reference. The executor must retain an incomplete receipt and must not report trust solely because the source file exists. A subsequent real refresh must finalize the receipt and establish independently verified trust. The corruption fault writes malformed bytes to this fixture's own receipt, proves revoke refuses before mutation, and restores the original local fixture bytes for cleanup. These are deliberate local faults, not simulated OS command responses.

This is native executor coverage. It does not claim signed-job validation, control-plane authorization, API dispatch, Windows store behavior, or an installed service journey. Those require their own suites. Missing prerequisites, failed refreshes, incomplete scenarios, and cleanup failures fail strict qualification. Neither this workflow nor the native store tests have been executed during implementation; full CI qualification remains pending.

Run through the workflow on disposable hosts. The script refuses ordinary local execution and requires an elevated Linux process, GitHub-hosted provenance, and `CERTOPS_LINUX_TRUST_DISPOSABLE_HOST=1`. Cleanup removes only exact fresh fixture anchor paths, refreshes the derived store, and verifies their absence. A failure in one deletion does not suppress other cleanup attempts; the VM/container is independently destroyed after the job.

The policy refusal case calls the actual native-platform agent trust-job executor with a valid renewal-only command policy. Both distribution and revocation must be rejected before native effects. Independently read anchor inventories, absence of receipts, and default OpenSSL distrust confirm no mutation. Public admin and approval authorization remain covered separately by the API trust suite.

The receipt-finalization case delegates the actual native refresh executable and preserves its unchanged result. Only after that command succeeds does the fixture move its own pending receipt aside and create an empty directory at the exact receipt path. The product must report installed OS state with receipt_finalize_conflict and intent_written. Independent default OpenSSL verification must prove trust. Restoring the original pending receipt must make revoke refuse; actual redistribution then repairs the receipt and native revoke removes the derived trust. The directory collision is an explicit local filesystem fault, not a simulated command outcome. The helper restores its held receipt in finally, and the shared owned-anchor cleanup still runs if an assertion fails.
