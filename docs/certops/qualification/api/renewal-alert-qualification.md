# Renewal outbox and SMTP qualification

The separate manual `certops-renewal-alert-qualification.yml` workflow executes eight mandatory supporting integration scenarios against only an isolated API, PostgreSQL and MailHog. The source admits a renewal through the production job service, claims it using a genuinely registered protocol client, reports a fixture failure through the real authenticated result endpoint, drains the production outbox resolver and starts the actual delivery-worker process. An independent MailHog receipt must match the run-owned recipient and MIME-decoded renewal subject. Terminal replay, public first-issuance failure, requester approval rejection and a completed dry run must leave one owned renewal alert.

The delivery child uses `NODE_ENV=production` and actual SMTP transport against the loopback fixture. `NODE_ENV=test` in the email helper intentionally simulates success, so a successful delivery database row is insufficient. The workflow starts no background test-mode delivery worker, preventing that simulated branch from racing the mandatory real receipt.

All eight cases passed focused execution. Independent strict report verification, current source digest verification and lint passed; hosted/full CI remains pending. Agent-local admission metadata for a real locally generated certificate/key is explicitly seeded as an initial supporting protocol prerequisite. The fixture does not claim native custody, actual certificate renewal failure, real CA traffic or delivery to an external recipient. Shared development databases are refused by the separate-stack opt-in and empty global agent/certificate/alert/outbox guards. The owned API process and label-verified PostgreSQL/MailHog containers were removed after testing.

## Native proxy refusal

The Ubuntu certbot bulk-scope journey can extend the same outbox and delivery path after a certificate is already serving. It admits one public renewal, then refuses `new-order` on the owned qualification proxy. The refusal is counted only for requests the proxy recorded and did not forward. The current claim fails, one nonce is consumed, and the serving certificate, private key and trusted TLS fingerprint stay in place. No additional issuance response is counted. This composition is a controlled proxy fault. It is not evidence of a native CA run.

The failed renewal must appear as one `renewal_alert_requested` outbox row, be resolved by the production outbox drain, and be sent by a one-shot `delivery-worker` process whose environment is `NODE_ENV=production`. MailHog, observed separately from the worker, must show exactly one new message for the run-owned recipient. The subject contains `Certificate renewal failed` and the body contains the failed job id. Re-draining the outbox must leave that single alert and that single message.

`NODE_ENV=test` makes the email helper return success without opening SMTP. That simulated success, and a delivery row that only says sent, does not count as the receipt. A planted inbox message does not count when the delivery child is in test mode. The production child forces loopback SMTP, clears inherited SMTP credentials, and the receipt gate accepts only `NODE_ENV=production` together with exactly one new matching message.

The native journey execution of this extension remains pending. The eight fixture scenarios above remain the executed evidence for a protocol-reported failure. The journey host must provide MailHog at `CERTOPS_NATIVE_RENEWAL_MAILHOG_URL` (default `http://127.0.0.1:8025`) and SMTP on `CERTOPS_NATIVE_RENEWAL_SMTP_PORT` (default `1025`).
