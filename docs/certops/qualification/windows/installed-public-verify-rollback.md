# Installed public renewal verification failure and rollback

This source composes the actual public manual-renewal route with the registered
LocalSystem agent, real ACME issuance and CNG acceptance, native HTTP.sys SNI
deployment, failed trusted-TLS verification and ordinary product rollback.
Native execution remains pending. It does not substitute an executor, CA result,
job outcome, clock or private key.

The owned fault is a concrete `127.0.0.1` IP certificate selector on the existing
primary port. It uses the **current predecessor certificate**, so trusted TLS
initially remains unchanged. The helper refuses any other supported IP/SNI
selector on that port, records a fresh shadow application identity and checks
the complete observed native tuple before removal. A second owned site on a
different port borrows the predecessor and independently checks unrelated
binding and trusted-TLS preservation. Its physical directory contains only an
owned public stub, and its original file/directory identities are checked before
removal. No public multi-target dispatch is implied.

The first actual public renewal must have a real installed-agent claim and one
attempt. Its final job must contain current-claim `validation.failed` evidence
for `iis-bind`, `VERIFY_FAILED` and `rolledBack: true`. Its actual durable
accepted-container receipt and native certificate/private-key association bind
the new CA leaf to that precise job. Native private signing and public
verification establish possession without exporting key material; the machine
chain and SAN are checked independently.

The intermediate SNI binding can be too brief for independent process-based
polling because a served fingerprint mismatch fails verification immediately.
The proof therefore explicitly does **not** qualify independent observation of
that transient new binding. It requires the real product outcome and its
current-claim evidence plus independent native accepted-custody and restored
binding/TLS facts; it never fabricates an observed intermediate state.

The predecessor's native selector, certificate, store, client settings, IIS
coordinates and trusted TLS must be restored. The product generates a fresh
HTTP.sys application GUID on both bind and rollback; primary AppID preservation
is explicitly not qualified. Helper-owned shadow and sibling AppIDs remain exact
cleanup ownership boundaries.
Only then is the exact shadow removed. A new public renewal must succeed with
a new claim, changed leaf, SPKI, serial and protected CNG key, matching persisted
verification evidence and managed inventory. Both the predecessor and the first
failed operation's accepted key remain owned and intact for the enclosing
journey's normal guarded cleanup. This helper never deletes those borrowed keys.

The proof explicitly excludes bind-failure qualification, failed rollback and
expiry reclamation. This is one supported My-store SNI target on the existing
hosted Windows fixture; it does not add explicit IPv6, centralized certificate
store, arbitrary service identity or multi-target product capabilities.
Installed public bind-failure injection and rollback is the separate case in installed-bind-failure.md.

A durable nonce guard and an in-memory ownership registry precede all native
mutations. Unexpected job state, changed endpoint/site/root identity or lost
receipts preserve the fixture rather than authorize broad cleanup. Successful
completion requires exact removal of both temporary endpoint resources and
fresh confirmation that the primary still serves the successful retry. This
is bounded ownership under an isolated disposable fixture, not an atomic
transaction against a malicious privileged actor changing machine state.

The actual Windows parent, reporter, producer and strict Node/Python projections require this named scenario and closed proof in all ten existing Server/key-profile cells. Current causal source fingerprints are mandatory. Supporting checks exercise missing/false/unknown evidence and real bounded sidecar lookup; native execution remains pending. No new native pass is claimed.

The two additional real renewal waits each have a 180-second bound. The normal
Windows lane therefore allows 32 minutes for the native test, 34 for its
producer, 37 for the SYSTEM completion receipt, 38 for the scheduled task and
51 for the workflow job. Supporting checks execute the actual producer with a
captured spawn and verify this finite nesting. The separate stopped/offline
lane keeps its existing limits. These budgets are bounds, not measured native
runtime or a permission to skip an unfinished mandatory scenario.
