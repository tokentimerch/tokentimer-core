# Installed Windows adoption and predecessor retention qualification

The trusted manual Windows ACME workflow invokes this journey on Windows Server 2022 and 2025 for RSA 2048/3072/4096 and ECDSA P-256/P-384. It runs inside the existing disposable API/PostgreSQL/Pebble fixture with the actual installed LocalSystem agent. Source implementation is present; Windows execution has not been performed during implementation.

The harness creates one unique operator-owned nonexportable machine CNG key, self-signed server certificate and IIS SNI site. The installed agent must discover and persist that actual certificate. Public authenticated renewal setup first runs as a dry run: the certificate must remain without a renewal profile, without a derivation intent, and bound to its original certificate and key. A second public request executes actual ACME renewal through the installed agent. Independent trusted TLS and native CNG inspection must prove the replacement certificate, rotated key and requested key size.

The production outbox drain then derives the actual renewal profile. This explicitly qualifies outbox processing called by the harness; it does not establish unattended worker scheduling. The native retention ledger must classify the outgoing certificate as preexisting. A fresh native process must read the same persisted ledger, and a deliberately incomplete owned atomic-write .tmp file must be ignored by the actual sweep. An actual retention sweep must defer removal for ownership_unrecorded, preserving its certificate and operator key while the replacement remains bound and serves trusted TLS.

Five named cases produce a separate strict windows-adoption-retention-real report. The runner independently checks every required case, measured Windows build and service process identity. The report records the source digest and distinguishes workflow checkout evidence from local worktree evidence. Missing discovery, native effects, prerequisites, or cleanup fail qualification.

Cleanup detaches adoption automation before removing its target, removes only the unique owned IIS/HTTP.sys binding, certificate fingerprints, known operator key and actual agent-issued receipts for this certificate, then independently checks key absence. On failure it first stops the service only after proving that its executable path belongs to the owned fixture. Broad inventory, additional retention eligibility gates, and private-key export behavior are separate scenarios and are not claimed by these five cases.

The operator certificate uses the supported [.NET Framework CertificateRequest and SAN APIs](https://devblogs.microsoft.com/dotnet/announcing-the-net-framework-4-7-2/). Native store reopening and independent HTTPS prove persistent key association; API availability alone does not qualify this journey.
