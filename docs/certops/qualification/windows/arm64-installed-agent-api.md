# Windows 11 ARM64 installed agent and API

The separate `certops-windows-arm64-agent.yml` manual workflow uses a disposable `windows-11-arm` desktop. It requires native ARM64 Node 24, PowerShell and the actual candidate-packaged service host. The original product installer runs unchanged at its canonical `C:\ProgramData\TokenTimerAgent` root, under SYSTEM, after proving both that root and the canonical service absent.

This lane covers real bootstrap exchange, registration, authenticated heartbeat, a public-created signed noop, a signed certificate **file-path dry-run plan**, actual My-store/CNG certificate discovery, service restart with fresh processes and heartbeat, protected configuration/credential/signing-pin preservation, original product uninstall and exact owned cleanup. The certificate plan uses the same production service admission as the existing Windows dry-run tests because the generic public job route cannot select dry-run mode. Public signed dispatch, claim, evidence and result routes remain real. A managed subject prerequisite, when necessary, uses the actual independently observed public native leaf and its real validity; this is not an adoption qualification.

The native certificate is independently checked for actual RSA2048, machine Software KSP custody, non-exportability, a matching public-key signature and unchanged DER/container identity. Agent-created My discovery evidence must match its fingerprint and actual registered agent. The plan performs no certificate deployment; the native certificate and discovery observation are separate controls. Issuance, ACME, AD CS, IIS, Windows Server and the broader full ARM64 certificate journey remain unqualified by this scope.

## Explicit PostgreSQL dependency architecture

The [current official hosted image inventory](https://github.com/actions/runner-images/blob/main/images/windows/Windows11-VS2026-Arm64-Readme.md) does not list PostgreSQL. This source therefore does not assume `PGBIN` or invent a native ARM64 PostgreSQL binary. PostgreSQL's [Windows port notes](https://wiki.postgresql.org/wiki/Windows) describe Windows ARM64 as unqualified upstream.

`scripts/certops-arm64-postgres-lock.json` pins the official EDB PostgreSQL **17.11-5 Windows x64** archive, obtained from the [EDB binary download page](https://www.enterprisedb.com/download-postgresql-binaries). Its actual reviewed download contained 381,531,864 bytes and SHA256 `80379b2c04d51c30225532e0ae04509899141e9957ed096fe749d7fd9df8f82f`. The download page's Windows17.11 link was `https://sbp.enterprisedb.com/getfile.jsp?fileid=1260616`, which redirected to the exact URL in the lock. This is an independently computed pin over the official HTTPS download, not a claimed EDB-published checksum or Authenticode verification.

The archive's five required tools were independently inspected as x64 PE files without executing them. The hosted lane must verify those headers again and actually start the owned cluster, migrate the application schema and obtain a real `SELECT version()` result. This dependency executes under **Windows11 x64 emulation**. Agent, Node, PowerShell and packaged service-host execution remain native ARM64. Missing emulation, archive drift or unsuccessful initialization fails the prerequisite; it never silently skips mandatory scenarios.

## Ownership and incomplete execution

PostgreSQL records original root/marker identity before the download, publishes a private preparation receipt, verifies owned binary/data directories and refuses cleanup after an uncertain startup. A confirmed cluster must stop through its exact data directory, with captured native descendants absent before root removal. Neither adapter terminates numeric PIDs. The connected cluster must independently report its exact owned data directory and its loopback listener must belong to the captured native PostgreSQL root process. The always-run cleanup stops/drains PostgreSQL but retains its data/root after any incomplete native agent journey; only a successful current-candidate native cleanup proof permits database deletion.

The agent journey verifies exact service command, SYSTEM account, original binary digest, private state directory and retained process creation identities. Destructive certificate cleanup requires the original native certificate/key association and the unchanged candidate-packaged ARM64 helper's complete machine-wide metadata inventory with zero surviving references outside the exact My certificate; unknown creation, changed custody or undrained processes preserves local and database ownership state. The scheduled-task driver only stops its exact nonce-owned task. An interrupted harness does not authorize an independent broad service/certificate deletion; the hosted disposable runner is discarded and no success proof is emitted.

This source and its pure/AST checks are implemented. The separate strict release cell, source fingerprints, closed Node/Python projection and manual-workflow provenance are wired. Hosted native execution and native qualification remain pending. Outer API or workspace cleanup failure invalidates the public report and preserves PostgreSQL data. It does not replace the full AMD64 workflows or the separate ARM64 CNG and SCM mock-child suites.
