# Two configured DNS resolver views

The disposable DNS routing fixture exercises the actual production DNS hook and provider against two separately owned native `pebble-challtestsrv` instances. Two loopback UDP forwarders preserve the original query and response bytes. This tests configured resolver disagreement; it does not qualify public recursive caches or authoritative DNS delegation.

The first real provider write appears only in the first view. Production `all` verification must refuse the reachable negative second view after repeated queries. A real provider write to the second view then allows `all` to succeed. A fresh owned record proves `quorum` with count one succeeds while the second view remains negative. Both endpoints must actually answer: an unreachable or skipped resolver cannot qualify. Production awaits both configured queries before deciding quorum; the fixture makes no early-return claim.

The harness requires Linux with Python/kernel pidfd support, its existing native DNS server on ports 8053/8055, the pinned native fixture executable, and disposable-host authorization. The additional instance uses 18054/18055; port 18053 remains reserved for the existing unreachable-resolver case. A controller retains the second process through a pidfd before executable entry; the caller independently checks its original process birth, executable and arguments before provider access. Shutdown uses the retained pidfd, never a numeric PID fallback. Each random label is independently absent before use. Cleanup refuses unexpected values because the native provider clears the whole label. Both actual provider views must be empty, UDP sockets closed, and the exact child waited with pidfd and controller closed before the ownership guard is removed. Unproven cleanup preserves the parent directory.

The proof contains only bounded counts and closed observation flags. Raw DNS packets, record values and process arguments are not report artifacts. The seventh mandatory scenario is wired into the existing manual Ubuntu routing workflow, with strict source fingerprints and release collection. Pure parser and proof checks do not constitute native execution. Protected native execution remains pending.
