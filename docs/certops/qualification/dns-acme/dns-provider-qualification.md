# Real DNS provider qualification

`certops-dns-provider-qualification.yml` manually qualifies all eleven production adapters against their actual provider APIs and native TXT resolution: Cloudflare, Route53, Azure DNS, Google Cloud DNS, RFC2136, acme-dns, OVHcloud, Hetzner, Infomaniak, Exoscale, and PowerDNS. It runs only on trusted `main`, uses two jobs concurrently, and serializes each provider with its independent janitor. No external requests or DNS mutations have been executed during implementation; the workflows require protected fixture configuration before full qualification.

Create one GitHub environment named `certops-dns-<provider>` for each adapter. Restrict it to trusted `main` and dedicated qualification credentials. Configure the secret `CERTOPS_DNS_CREDENTIALS_JSON` using that adapter's documented credential shape. Configure `CERTOPS_DNS_ZONE` and `CERTOPS_DNS_RESOLVERS_JSON` (a JSON array of native DNS resolver addresses). Use an isolated test zone and credentials limited to its required DNS operations. The harness checks local credential configuration, not the provider account's complete IAM policy; do not describe that prerequisite as independent proof of least privilege.

The only mutation target is `_acme-challenge.certops-qualification.<zone>`. Reserve that exact label for these tests. Preflight refuses any existing non-fixture TXT value. For acme-dns, configure a dedicated account and this exact label's CNAME to its assigned domain; a production ACME account must not share the fixture. Choose resolvers that can independently observe the selected zone and CNAME, including an appropriately reachable authoritative/test resolver for private RFC2136 or PowerDNS environments. Missing credentials, unreachable resolvers, failed API operations, and missing reports fail qualification rather than silently opting out.

Four mandatory cases create fresh challenge values, retain both concurrently submitted values, clean the first without deleting the second, and clean all owned values. Two actual Node processes submit their values concurrently through the production solver and its normal shared-host file locks. They perform real authentication and DNS operations with the shipped retry behavior. A separate native Node DNS resolver observes actual TXT records with bounded propagation waits. No provider response, socket, resolver, or HTTP transport is replaced with a fixture. Reports identify the actual adapter and classify this as integration evidence, not a complete certificate issuance journey.

Every value carries a reserved prefix, creation timestamp, and random identifier. An atomic local receipt is written before each potentially uncertain API mutation. The workflow's unconditional recovery step retries cleanup of those exact values after a failed test. The separate hourly `certops-dns-fixture-janitor.yml` observes the reserved label and removes only valid fixture values older than two hours. It preserves other values, requires the same dedicated environment, and serializes with qualification. Configure environment protection so scheduled cleanup can run on trusted `main`; a required human review on every scheduled job would prevent this safeguard from operating unattended.

acme-dns has no deletion operation: it deliberately keeps two rotating TXT slots. Its mandatory cleanup cases verify the documented no-op semantics and coexistence, and its report explicitly says `not-applicable-two-slot-provider`. Neither the test nor the janitor claims deletion or account removal. The dedicated existing fixture account retains only harmless qualification values until later updates rotate them out.

Credentials exist only in the protected process environment and solver memory. They are never written into receipts, command arguments, logs, or uploaded reports. Provider bodies and errors are withheld. Uploaded artifacts contain only sanitized named outcomes; raw resolver values and receipts are excluded. The runner requires GitHub-hosted provenance and `CERTOPS_DNS_DEDICATED_FIXTURE=1` before mutation.

These workflows do not qualify CA issuance, full account/EAB behavior, every provider pagination/auth/error branch, network interruption after a committed provider mutation, or multiple hosts modifying the same RRset. Those remain separate scenarios. Azure DNS tests use an existing dedicated DNS fixture; they do not provision a Windows or Azure VM lab.
