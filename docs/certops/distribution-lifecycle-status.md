## Requirement classification

“Fully implemented” describes the bounded, non-destructive control-plane behavior covered by automated tests. “Implemented but not production-qualified” means executable code exists and its listed tests pass, but an integrated real-agent/provider campaign and operational acceptance are still required. “Partially implemented” identifies exactly what exists and what does not.

## Review and deployment boundaries

- Review as a draft feature PR, **not** a production-qualified release or closure of unmerged provider/service extensions. New lifecycle flows and cleanup need the stated real-host/channel campaigns; unsupported connector/provider capabilities remain unavailable.
- Run the composed plan before updated API/workers: fresh main 79–81, lifecycle 82–86, compatibility schemas 87–90 and resolution delivery 91. Applied preview rows never move. Allow time for consumer-outcome/recovery backfills. Existing workspaces stay manual, recurring verification/alerts disabled and cleanup disabled/report-only. Retained mutating deployments and every cleanup require independent approval. Use the compatibility matrix; unknown histories fail closed.
- Upgrade API, worker and agents together before enabling calendars. `maintenance-calendar-v1` is an additional fresh-capability requirement; it does not relax existing material publication/deployment release gates.
- Scheduler and monitoring sweeps use independent `CERTOPS_SWEEP_DISTRIBUTION_SCHEDULER_*` and `CERTOPS_SWEEP_DISTRIBUTION_MONITORING_*` enable/timeout controls. Explicit group policies still control execution and notification.
- Run integrated real renewal → customer-store publication → bounded multi-host activation → fresh served/trust proof → drift incident → real channel delivery → recovery campaigns before production enablement. Include offline hosts, delayed approvals, expiring windows, worker restarts and reviewer revocation.
- Keep Windows/OpenBao/Azure production gates disabled and import no temporary trust exceptions. Schema/contract compatibility is covered here; the related runtime implementation and protected qualification remain separate integration/release requirements.
- Cleanup additionally requires native qualification of its new, currently undeclared capability plus the runtime, group and customer-local opt-ins described in the [cleanup protocol](distribution-retention-cleanup.md). A permanent fence survives cancelled/expired authority and uncertain effects; no API silently makes that UUID deployable again.
- Review operational scale limits: group-level verification waits on blocked required consumers; next-window search is bounded; management reads are bounded; queue admission caps incident bursts. These fail conservatively but need fleet-level acceptance.
- No branch merge, release, protected qualification dispatch, customer-local mutation or real notification delivery was performed by the local checks.
