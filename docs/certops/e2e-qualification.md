# Certificate lifecycle E2E qualification

Browse the [topic index](qualification/README.md) for Windows/AD CS, Linux, DNS/ACME, Kubernetes, API/worker, edition and reporting runbooks. This page remains the entry point for the overall qualification model.

The scenario specifications in `e2e-scenario-catalog.json` describe intended outcomes across certificate discovery, Windows services, CNG, IIS, ACME, AD CS, renewal, CSR, deployment, trust, controllers and edition policy. A planned scenario is not a passing test. Its environment and implementation must be assigned before qualification.

Full E2E uses the actual product API or browser, worker/database, installed execution plane, issuer and destination. Verify public certificate bytes and the served TLS leaf independently of the job result. Module drivers provide host integration evidence; mocked or seeded results must retain their narrower classification.

Qualified runs require explicit prerequisites and named scenario execution. Missing tools, skipped mandatory cases, absent reports and an empty selection must fail. Developer runs may skip unsupported hosts with a reason. Reports must identify the exact candidate commit/package, environment, identity, outcomes and cleanup.

Run hosted Windows qualification on disposable machines with unique services, sites, bindings and work directories. Preserve trusted-reference workflow policy. Enterprise AD CS qualification requires the full ADR-0014 matrix under the actual service identity; standalone CA smoke cannot replace it. The shipped AD CS capability remains gated until release qualification is complete.

The domain-backed matrix preserves the production limit of 20 issuer preflights per workspace per hour. Unsafe-template and CA-flag probes use disposable preflight-only workspaces, each with its own real bootstrap, registered candidate CLI agent and protected state under the guest's independently verified `LocalSystem` identity. Each cohort permits at most 18 actual public dispatches. Unchanged primary CA/template facts may be reused; native first-submission safety checks still run, and flag or CA-key changes invalidate the affected cached context. Cleanup independently counts persisted jobs, stops owned children before removing state, and deletes the cohort users and workspaces. No preflight timestamp or rate-limit policy is rewritten.

Native validity-boundary cases use public frozen enrollment policy: an actual two-day pending certificate approved against an installed six-day certificate must fail `requireLaterNotAfter`; an actual six-day issued certificate must fail a seven-day `minimumRemainingValidity`. Both require CA-signed public certificate evidence, refusal before acceptance, exact unaccepted CNG-key cleanup and unchanged outgoing trusted IIS TLS. Agent and CA clocks remain actual. These are implemented source cases pending native matrix execution.

Live template mutation cases additionally snapshot the owned safe template's public LDAP attributes under an exclusive invocation-bound receipt, then exercise prohibited EKUs, absent or unsafe application policies, schema one, incompatible schema-three algorithm metadata and unreadable required constraints. The original confirmed primary issuer dispatches a genuine signed enrollment after a real service restart. Each refusal must allocate neither a native CA request nor a CNG key and must preserve the existing trusted IIS TLS certificate. The fixture restores and rereads the exact original attributes and restarts the candidate again before proceeding. Unsafe preflights remain within the separate real-agent cohort budgets. Native rendering and LDAP behavior still require the qualification matrix; source cases do not count as observed execution.

The native retrieve boundary cases independently observe the CA request head before querying an absent request, and create a genuine officer-requested certificate before querying it under the original machine identity. They require numeric `0x80094004` and `0x80070005` uncertainty outcomes respectively, no returned or imported certificate, unchanged enrollment journal and no additional CA request. The foreign fixture retains an exclusive invocation-bound public ownership receipt until its exact CA row is revoked and its temporary nonexportable key is removed. These exercise the real native issuer boundary; they do not fabricate an uncertain server enrollment or replace the separately isolated response-loss experiment.

Keep independent TTL cleanup for disposable enterprise infrastructure. Do not infer successful cleanup from successful tests or rely solely on workflow finalizers after cancellation. No production CA or certificate-store resources belong in fixtures.

The enterprise AD CS recovery helper operates on genuine pending requests from the disposable lab. It restarts the actual owned SCM service, checks durable CSR/key/request identity, and races four supported scheduler calls while requiring exactly one signed continuation and unchanged native CA request count. Public abandon must refuse a pending request without freeing its protected key. A separate late approval occurs only after the agent has acknowledged expired-key cleanup; the actual CA must issue, while the enrollment stays expired and its key and IIS binding stay absent. Scheduler eligibility uses the supported `now` parameter; agent and CA clocks, journal contents and database expiry are not rewritten. These source cases require native qualification and do not qualify crashes during submit, acceptance or individual installation steps.

The separate manual journal-phase experiment observes a real durable `keygen_intent`, `prepared`, `submitting`, or initial `installing` journal and terminates only the independently verified owned LocalSystem agent/SCM process tree. It refuses a missed phase window or changed process identity. Only the owned fixture service has automatic SCM recovery temporarily disabled during fault observation; finalization restores the product installer recovery policy and verifies the original native policy bytes. The experiment uses the supported disposable controller lease/grace settings of 60 seconds each, waits for actual time and the production lease reaper to mark the job `orphaned_unknown_effect`, and invokes the audited public recovery endpoint. It never rewrites a journal, job phase, lease timestamp or database clock. Key-generation interception additionally requires an actual owned `certreq -new` process and a non-exportable machine CNG key before termination. With no durable CSR, audited recovery must refuse `ADCS_RECOVERY_CSR_REQUIRED` and preserve that exact protected key; supported public cancellation must then remove it without creating a CA request. A missed key-generation window fails the experiment. Prepared and installing recovery must preserve CSR/key identity and serve trusted TLS; uncertain submission must create no additional CA request and needs actual operator reconciliation or abandonment. The report remains `not-qualified` and is excluded from the release collector until native runs prove the fault interception. Validation of these short fixture timing settings cannot qualify the default 15-minute lease, one-hour grace, deferred validation, or every installation-step crash.

The installation recovery API suite independently tests real HTTP, authentication, PostgreSQL row locking, concurrent request reuse, audit/requester provenance, unknown-effect acknowledgement, terminal-state refusal, workspace pause and approval/self-approval policy. Its failed-installation and orphaned-job prerequisites are explicitly seeded server fixtures; a protocol-only Windows identity does not claim Windows, CA or CNG execution. This focused API suite passed locally and complements the genuine enterprise host cases.

## Commands and current implementation

Qualification entrypoints retain `certops-*.yml` filenames and use a `CertOps / ` display-name prefix in the Actions sidebar, separately from normal CI. Keep runnable YAML directly in `.github/workflows`: GitHub [does not support workflow subdirectories](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows#creating-a-reusable-workflow). The substantive harnesses, fixtures and infrastructure are already grouped under `scripts`, `tests/e2e`, `packages/agent/scripts/host` and `infra/certops-adcs`. Moving an entrypoint into a workflow subdirectory would prevent GitHub from discovering it; it would not create a CI category.

Run `pnpm test:certops:qualification` for the focused gate/report regression tests and `pnpm check:certops:catalog` to validate specification mappings. These commands do not run full CI or mutate host certificate stores.

The trusted `certops-qualification.yml` workflow runs Windows Server 2022/2025 host qualification and a disposable PostgreSQL agent protocol suite. Windows host execution is explicitly opted in with `CERTOPS_HOST_TESTS=1`; strict reports require the candidate SHA and committed mandatory scenario IDs. The Windows suite covers native discovery/fingerprint, RSA/EC CNG CSR generation, isolated IIS cutover/rollback, cleanup and supporting Go module assertions. Go results are labeled unit evidence. These paths have implementation coverage; actual hosted execution evidence must still be collected.

The standalone AD CS manual workflow measures native CA feasibility, certreq/CNG and an owned IIS SNI deployment with an independent trusted TLS fingerprint check. It refuses existing CA resources and installation reboot requirements. Cleanup removes the owned binding/site, leaf key and CA certificates, and removes only newly installed roles. Its report explicitly excludes domain membership, Kerberos/template permissions and the full product enrollment journey. It does not enable the released AD CS capability. Actual hosted feasibility remains pending.

The catalog specifications retain planned or partial status where their complete journey is missing. Separate workflows now cover installed-service Windows ACME, disposable enterprise AD CS infrastructure with an independent TTL janitor, [Linux certbot and acme.sh issuance/renewal](qualification/linux/linux-acme-qualification.md), [native Linux trust stores](qualification/linux/linux-trust-qualification.md), Kubernetes and the dashboard. Their implemented subsets and outstanding variants are recorded in the catalog and lane documentation. Native execution and release qualification remain separate from implementation coverage.

## Authenticated API journeys

The isolated stack qualification includes public CSR lifecycle, real TLS inventory observation/rotation, and certificate governance suites. They use real sessions/CSRF, migrations and public routes. Independent OpenSSL and TLS observations check public material; test database queries check persisted identity, history and atomicity rather than fabricate the business outcome.

CSR confirmation is explicitly manual attestation. The inventory and governance suites use an actual HTTPS endpoint and real monitor scan. Their local focused runs have separate sanitized source-digest reports; they do not establish a released artifact's qualification. Fixture cleanup requires `CERTOPS_CSR_DISPOSABLE_STACK=1`, removes only run-owned resources and audit rows using the existing test pattern, and always deletes temporary private-key material.

The named supporting integration matrix covers existing controller, inventory, trust, identity, jobs, worker, CSR and AD CS database/API tests. Expected sources and test names are committed. It rejects absent, skipped, failed or duplicate required cases and does not label mocked host operations as real-host proof.

## Disposable Kubernetes lane

`certops-kubernetes-qualification.yml` is a trusted manual host integration lane. It creates an isolated kind cluster, installs versioned cert-manager, and calls the product Certificate provisioner with an actual kubectl-backed client. The tests prove owned resource creation/idempotency, Ready issuance, independently parsed public `tls.crt`, and local workspace/cluster/namespace policy refusal. The adapter does not read or serialize `tls.key`.

The lane also builds the candidate production controller image and runs its actual in-cluster client inside a bounded pod. Mounted service-account credentials permit only Certificate get/list/watch/create/patch in the owned namespace. The pod exercises create, unchanged reconciliation, list and a native watch update after merge patch; cert-manager must issue the updated public leaf with both requested names. Recreating the client must preserve resource UID and idempotency. A separate read-only identity must be denied Secret creation, CertificateRequest patching and Certificate deletion. A second production-image pod uses that read-only identity: actual provisioner create and patch calls must receive Kubernetes 403, while independent reads prove the owned resource unchanged and the refused resource absent.

Administrative fixture access creates the namespace, issuer and scoped identities, and the host provisioner tests use a local mutation authorizer. The separate [controller API journey](qualification/kubernetes/kubernetes-qualification.md) runs the production controller with real public intents, scoped command authorization, persisted observations, a served TLS destination, API outage recovery and pod restart. Owned namespaces are deleted by the harness and the complete disposable cluster is removed by unconditional workflow cleanup. The native cluster lane has not yet been executed during implementation.

Fixture versions follow the [cert-manager supported release matrix](https://cert-manager.io/docs/releases/) and [official kind node image releases](https://github.com/kubernetes-sigs/kind/releases). The Kubernetes node image is digest-pinned; cert-manager uses a fixed chart version. Re-evaluate compatibility when upgrading these fixtures.

## Real dashboard lane

`certops-browser-qualification.yml` starts the actual dashboard and disposable API/PostgreSQL stack, installs the locked Playwright Chromium build, and runs `scripts/certops-browser.js`. No requests are intercepted. The suite exercises form login, actual certificate navigation, phone-width navigation, pause/resume and approval persistence checked independently through API reads, public CSR submission/import/manual attestation, and AD CS wizard prerequisite refusal. The latter cannot replace a successful safe preflight with a real domain agent.

Three additional required browser cases open the actual renewal-profile disclosure, switch automatic renewal off and on through its confirmation dialog, change the lead time, and cancel both a lead-time edit and a renewal-disable confirmation. Public API reads and page reloads verify persistence, unchanged execution policy, and no job creation. The public policy row is a seeded supporting prerequisite; these controls do not claim successful issuance or native renewal. A separate failed-save case revokes the run-owned user's administrator role after the form loads: the actual backend returns HTTP 403, the UI displays its error, and the approval setting remains unchanged before and after reload. The original role is restored in a finally block. All sixteen browser cases passed focused local execution against the disposable API/PostgreSQL and actual dashboard. Hosted workflow and edition-specific browser qualification remain pending. A missing Chromium runtime is reported as a failed browser capability check.

The private-key refusal case generates disposable EC material in memory and tries raw and base64-wrapped input through the actual CSR dialog. A passive request counter must observe no CSR submission, and an independent API read must show unchanged workflow inventory. The listener retains no request bodies. A separate keyboard case opens the dialog with Enter, checks focus containment through Tab navigation, and requires Escape to restore focus to its opener.

The viewer case uses a separate real account with admin access to its own workspace and viewer access to the test workspace. Direct navigation to the latter's CertOps settings must redirect to the dashboard, and a real authenticated settings write must receive 403 without changing approval policy. Cleanup includes only workspaces owned by each unique fixture account, including automatically created personal workspaces.

The machine-token browser case creates an actual scoped token, requires acknowledgement before closing its one-time display, verifies that API listing and a reloaded inventory do not expose the credential, and revokes it through the UI. A real bearer-authenticated executor request must authenticate before revocation and return 401 afterward. Credentials remain in memory and are excluded from reports.

Only the sanitized named report is uploaded. Browser traces, cookies, temporary credentials and private signing fixture files are excluded. The fixture requires explicit disposable-stack authorization and attempts API cleanup even if browser launch or preflight fails. Responsive navigation and emulated color schemes provide interaction coverage; visual contrast and all edition layouts need their own qualification.

[Issuance admission and pause qualification](qualification/api/admission-and-pause-qualification.md) covers public first provisioning, fresh command declarations, stopped management periods, and ingestion of already-owned results during a workspace pause. These focused API suites supplement native execution journeys.

The manual historical API migration workflow uses the immutable Core commit `b6ad7fc3d38db35b4c41a2c6137b0c39afc72158` and the exact candidate checkout, installing each from its own frozen lockfile. Its fresh PostgreSQL 16 service uses an independently assigned port and database; it refuses an existing schema or the local development fixture port. The historical API creates real public jobs, imports and signed pending CSR workflows, with a live TLS monitor. The candidate must apply additional migrations, preserve their frozen identities and payloads, enforce independent approval, and promote the historical CSR from an actually served replacement certificate. A second candidate startup must leave schema and promotion identities unchanged. Only authentication identities/memberships are fixture seeded; completed jobs, enrollments, installation receipts and observations are never injected. Reports record source commits, lockfile hashes, actual PostgreSQL image identity/version and migration/table/column counts. The focused local run passed all six scenarios against separately owned API processes and PostgreSQL, applying migrations 69 to 72 (65 to 68 tables and 855 to 899 columns), then destroying its database container. Its report explicitly records local worktree provenance and cannot satisfy trusted release qualification. This is source upgrade qualification, with full workflow execution pending; published release packaging and historical AD CS enrollment/service receipt migration require separate coverage.

The native Windows registration fixture independently checks `CERTOPS_AGENT_REGISTRATION_CONFLICT`, preservation of unused bootstrap authorization and predecessor state, then registers an independent replacement in separate protected state. Its existing-credential observe-only restarts must publish profile addition followed by empty removal and withdraw log streaming when disabled, without changing credential, identity, signing-key pin or assigned work. These focused native API/agent checks passed locally. The full installed journey additionally checks predecessor service credentials and served TLS; a replacement SCM handoff and predecessor custody transfer are not implied by the process fixture.
